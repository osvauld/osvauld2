# W2 — Lua app layer v1 + drop targets (2026-07-28)

The MVP-first pivot lands here: instead of more M0 leaf/infra polish (rich text, focus,
IME), W2 pulls the **app layer** forward — the fastest path to a *running, agent-authorable
app*. Two proofs this week:
- `todo.lua` (adapted) renders on the new runtime — scrolls, hovers with fade, adds on Enter.
- a minimal **kanban** proves **drag-and-drop with a preview** — a card lifts, follows the
  cursor, and drops into another column.

Companion: `runtime-3month-plan.md` (the *when*), `runtime-rebuild-plan.md` (the *what/why*).
Reference-only: `app_engine/` (the old host) + its 17 example apps — read for the decision
list, **not** copied. We rewrite the whole app layer on our terms; the old code's job is to
keep us from rediscovering its bugs.

**Scope note (compression).** We know far more now — the old engine is a pre-solved decision
list and the W2 research settled the architecture (the 3-layer split: Lua tree → keyed
nodes over the doc → retained islands), so there's no design-exploration time to spend. The
host proper compresses to **~3 days**; drop targets add **~1 day**; the week is full but not
overloaded.

## Goal
Stand up a sandboxed Luau VM whose `view()` walks directly into `El<LuaMsg>` — the same
builders shell2 uses, no parallel node type. A `doc` binding exposes the app's state store.
Two example apps prove the loop end-to-end: `todo` (setup → view → click closure → mutate →
next view reflects it) and `kanban` (the same loop + drag-and-drop).

## 1. Integration theory — the one type decision  (LOAD-BEARING)
Theory: a Lua app is just an **MVU** app (Model-View-Update) whose message type is "call
closure #n". The walk pushes each `on_click`/`on_input`/`on_drop` closure into a per-frame
`handlers` vec and the `El` carries an index. Dispatch calls the closure, the closure
mutates the doc, `view()` re-runs. **The runtime's update loop does not change at all** —
Lua apps are ordinary apps whose `M` happens to be an index.
- [ ] `enum LuaMsg { Call(u32), CallStr(u32, String), CallPos(u32, f32, f32) }`
- [ ] handlers vec rebuilt every `view()`; index rides on the `El`, resolved at dispatch
- [ ] `Call` = zero-arg (`on_click`); `CallStr` = input string (`on_input`); `CallPos` =
      `(x,y)` — reused for `on_drag` (DragEvent → pos) and `on_drop`

## 2. Luau VM + sandbox
Theory: apps are untrusted code; this is the only sandbox boundary. Luau's own knobs
replace the old engine's hand-rolled ones — `sandbox(true)` instead of scrubbing
`load`/`dofile`/`loadfile` by hand, `set_interrupt` instead of instruction-hook counting.
The research confirmed the two non-negotiables below (Luau guarantees memory-safety from
untrusted *source*, but **not** from bytecode and **not** against resource exhaustion — those
are ours). Ported *shape* from `app_engine/src/script/vm.rs`, not its code.
- [ ] `Lua::new()` + `sandbox(true)`; allocator memory cap (`set_memory_limit`)
- [ ] **compile from source, never load bytecode** — line numbers in tracebacks *and* it's
      the boundary Luau's safety guarantee actually covers
- [ ] `set_interrupt` instruction/wall budget, **reset before every entry** (per-`view()`/
      per-handler, never cumulative — the old engine's key lesson)
- [ ] `require` shim over the app's files (no `package` lib): `lib/x.lua` →
      `require("lib.x")`, lazy, loaded-cache with `false`=in-progress (require-cycle catch)
- [ ] `now()` — epoch seconds, the one ambient capability
- [ ] **Done when:** a trivial app loads and `view()` runs; an infinite loop is killed by
      the interrupt budget with a real line number

## 3. Prelude + walk → El<LuaMsg>  (the real work)
Theory: `ui` is a ~15-line injected Lua prelude — each `ui.foo` tags a plain table with its
kind. The walk in Rust matches the tag and calls the **real `El` builder** (`col()`,
`.fill()`, `.on_click(LuaMsg::Call(idx))`). No intermediate `Node`+`Style` world to
reconcile — one vocabulary, one validation point. Reference the old `walk` in
`app_engine/src/script.rs` for the tag set + arg shapes only.
- [ ] prelude: `ui.col/row/text/button/input` tagged-table builders (string/number arg =
      one-element table sugar)
- [ ] walk: `col`/`row` → `col()`/`row()` + children (array part / `table.unpack(rows)`)
- [ ] `text`/`button` → `text()` leaf; `button` is a text leaf that usually carries
      `on_click`
- [ ] any node may carry `on_click = fn` → push handler, `.on_click(LuaMsg::Call(idx))`
- [ ] `scroll = true`/`"x"`/`"y"`/`"both"`/`"name"` → `.scroll_y(id)` etc.
- [ ] **keys: reuse retained state by a data-derived key (the row/card's doc id), never the
      loop index.** The single most-documented failure mode in React/Flutter — and kanban is
      the exact app that triggers it (a dragged card's state reattaches to the wrong card on
      reorder). Non-optional the moment kanban is in scope.
- [ ] unknown tag → a rendered error string, not a panic (every entry fallible)
- [ ] **Done when:** a hand-written `ui.col{ ui.text{...}, ui.button{ on_click=... } }`
      renders the same pixels as its Rust `El` twin; the click dispatches

## 4. Style parser → taffy / peniko
Theory: port the CSS-ish vocab from `app_engine/src/script/style.rs` — same key names and
token grammar, but resolving to our `Style` (taffy) + `peniko::Color`. Mechanical: the
parser logic is right, only the output types change. (Note: we commit fully to taffy
flex/grid — no hybrid unit escape hatch. Roblox's `UDim2` dual-coordinate system is the
survey's single most-hated wart.)
- [ ] lengths: `24`, `"24px"`, `"50%"`, `"1.5rem"`, `"auto"` → our `Val`/taffy dimension
- [ ] edges (`padding`/`margin`): number = all sides; `"10 20"` CSS 1/2/3/4-value shorthand
- [ ] `background`/`color`/`border`/`border_radius`/`box_shadow` via `csscolorparser` →
      `peniko::Color` (Color32 → `Color::from_rgba8`)
- [ ] flex: `direction`/`gap`/`grow`/`justify`/`align_items` → taffy
- [ ] `font`/`font_size` → `TextSpec`
- [ ] **Done when:** `todo.lua`'s `S` style table parses and lays out identically to a
      hand-built Rust equivalent

## 5. doc binding — the app's state store
Theory: `doc:list/map/text` open named top-level Loro containers. **We treat Loro as a
local, single-writer document store this week — its CRDT-ness (merge, concurrent stable
ids, mark expansion) is for *sync*, which defers with iroh/peers.** Single-writer, the
binding is simple, and we get **persistence for free** (state survives restart). We keep the
old scar — **re-resolve handles by name/index every access, never cache** (cheap insurance,
matters once sync exists). Port the non-egui parts of `app_engine/src/script/crdt.rs`.
- [ ] `doc:list(name)` → MovableList: `#`, `:get(i)`, `:add{…}`, `:remove(i)`, `:move(f,t)`
      (all 1-based) — `:move` is what kanban reorder/cross-column uses
- [ ] `:add` stamps a stable id at birth (app-supplied string id wins; reject dupes /
      `#`-prefixed) — this id is also the retained-state key from §3
- [ ] `doc:map(name)` / `list:get(i)` → map: `m.key` (Index) / `m.key = v` (NewIndex,
      `nil` deletes)
- [ ] `doc:text(name)` → LoroText: `:get()`, `:set(s)`, `#`
- [ ] scalar coercion both ways (bool/i64/f64/string ↔ Lua); nested containers = nil for now
- [ ] **Done when:** todo's `add`/toggle/`remove`/`set` and kanban's cross-column `:move`
      round-trip through the doc and survive a restart

## 6. Input — the honest cheat
Theory: the old engine bound LoroText *directly* into the editor via a `TextBuffer` trait
(no round-trip). Our `input()` is MVU string round-trip today, so v1 spells the draft field
as read-value + on_input:
```lua
ui.input{ value = draft:get(), id = "draft", on_input = function(s) draft:set(s) end,
          on_submit = add_draft }
```
- [ ] `input` tag → `input(value, id, map=CallStr)`; `on_submit` → `.on_enter(Call)`
- [ ] `draft:set` = delete-all + insert — **flagged**: bad CRDT hygiene under concurrent
      edits, fine single-writer. Fixed when the Field binds LoroText directly (later).
- [ ] **Done when:** typing the draft + Enter (or the add button) appends a task and clears
      the field; focus stays for the next entry

## 7. Host integration
Theory: a loaded `Script` is just an app in shell2 — its `Model` holds the VM, its `view`
runs `Script::view()`, its `update` matches `LuaMsg` and dispatches the closure.
- [ ] `Script { lua, view_fn, handlers, doc }`; `load(source, doc) -> Script`
- [ ] `view(&mut self) -> El<LuaMsg>` (walk, collecting handlers)
- [ ] dispatch: `LuaMsg::Call(i)` → `handlers[i].call(())`; `CallStr`/`CallPos` pass args; a
      handler error surfaces (does **not** replace the running view)
- [ ] mount two hardcoded apps (`todo`, `kanban`) in shell2 behind a dev route
- [ ] **Done when:** `todo.lua` and `kanban.lua` both run live in shell2

## 8. Drag-and-drop — drop targets  (the kanban primitive)
Theory: we have the drag *gesture* (phases + capture from W1) but not the *drop* half.
Decomposed, most of it already exists:
- **Preview** (card floats at cursor) = **composable now** — an `overlay` with a **Point
  anchor** (built W1) pinned to the live pointer, showing the card. The app holds
  "which card + where" in its model, updated by `on_drag`, and renders the ghost. Immediate
  mode gives it for free.
- **Placeholder** (the gap where it lands) = **app-level**, once drop targets report hover.
- **Drop targets** = the *one genuinely new runtime primitive* below.

Runtime (Rust) work:
- [ ] expose the **live pointer** to the view during a drag (DragEvent carries current pos)
- [ ] **drop-target registry + hit-test**: an `El` can mark itself a drop zone; during a
      drag the runtime hit-tests the pointer against zones and reports the one under it
- [ ] fire **`on_drop`** on the target when the gesture releases over it (which zone +
      what's being dragged)

Walk (Lua) work:
- [ ] `on_drag = fn` → `.on_drag(id, map)` (already in `el.rs`) → `CallPos`
- [ ] `drop_target = true` / `on_drop = fn` on `ui.col`/`ui.row` (a column) → registry + `CallPos`
- [ ] preview via `overlay = { panel = card, at = Point(pointer) }` — reuses W1 Point anchor
- [ ] **Done when:** in kanban, a card lifts under the cursor, columns highlight as you drag
      over them, and releasing calls `on_drop` → `list:move`/cross-list reparent; the board
      re-renders with the card in its new column
